## Finding 1: Installed functional smoke test uses keyboard events for manager navigation, not physical or kernel-backed controller input
- Requirement: SPEC §11.1.5 — "hotplug a physical or kernel-backed synthetic controller, navigate Manager with real controller events." SPEC §5.7 — "Controller acceptance uses the production controller transport with a physical or kernel-backed synthetic gamepad while InputPlumber is running; keyboard-generated SDL events are supplemental accessibility evidence and must never be labeled controller acceptance." SPEC §11.1.5 — "Missing backend, skipped package build, expected early exit, keyboard-only interaction, or a merely nonblank window is failure, not a skip."
- Production evidence: The installed binary tests (`tests/test_installed_binary.sh:331–342`, `tests/test_installed_smoke.sh:216–222`) navigate the manager using `xdotool key Tab`, `xdotool key Down`, and `xdotool click 1` — keyboard and mouse events, not controller events. The kernel-backed controller test (`tests/test_kernel_controller.c`) skips with exit 77 because `/dev/uinput` is unavailable. The `physical-controller` and `kernel-uinput` capabilities are not declared in `.factory/environment.toml` and have no runner evidence. The campaign-required `installed-package` capability is likewise undeclared and unevidenced, meaning the installed tests run in the build environment, not a clean installed-package runner.
- Required remediation: A fresh plan must schedule acquisition or declaration of a runner with `physical-controller` or `kernel-uinput` and `installed-package` capabilities, then run the installed functional smoke test with a physical or kernel-backed synthetic gamepad navigating the installed manager binary. The test must verify semantic outcomes through real controller events, not keyboard proxies.

## Finding 2: Controller-path interaction acceptance relies on process-local SDL virtual gamepads, not physical or kernel-backed input
- Requirement: SPEC §5.7 — "Controller acceptance uses the production controller transport with a physical or kernel-backed synthetic gamepad while InputPlumber is running." SPEC §11.2 criterion 3 — "Every enabled control in the §5.7 inventory has passing controller and pointer activation evidence" through production dispatch.
- Production evidence: The native interaction tests (`tests/test_manager_native.c:118–124`, `tests/test_manager_native_prof.c`, `tests/test_overlay_native.c`) use `SDL_JoystickAttachVirtual` to create process-local virtual gamepads. While these dispatch through the production `cbx_manager_handle_event` path and verify semantic outcomes, SDL virtual gamepads are not physical or kernel-backed devices — they are in-process software constructs that bypass the kernel evdev layer. The `test_kernel_controller.c` test, which would provide genuine kernel-backed evdev input via `/dev/uinput`, skips with exit 77. Neither `physical-controller` nor `kernel-uinput` capability is declared or evidenced in the environment.
- Required remediation: A fresh plan must schedule a runner with `physical-controller` or `kernel-uinput` capability and rerun the interaction inventory's controller-path acceptance (50 verified entries) using a physical or kernel-backed synthetic gamepad. The existing SDL virtual gamepad tests may remain as supplemental evidence but must not be the sole controller-path proof.

## Finding 3: GPU backend smoke coverage is skipped — no gpu-compositor capability declared or evidenced
- Requirement: SPEC §11.1.6 — "Exercise the deployment renderer backend (OpenGL/OpenGL ES where available) with broad framebuffer invariants. Deterministic golden comparison may remain on the software renderer, but successful object creation or draw calls alone are insufficient for hardware-backend acceptance."
- Production evidence: `tests/test_backend_smoke.c` is registered with `SKIP_RETURN_CODE 77` and skips because no GPU is available in the declared environment. The `gpu-compositor` capability is not declared in `.factory/environment.toml` and has no runner evidence. The software-renderer backend smoke (`test_backend_smoke_sw`) passes, but the spec requires exercising the deployment (hardware) renderer backend as a distinct layer.
- Required remediation: A fresh plan must schedule a runner with `gpu-compositor` capability and run `test_backend_smoke` (or an equivalent hardware-backend framebuffer invariant test) to completion, verifying OpenGL/OpenGL ES rendering produces valid output beyond object creation.

## Finding 4: Human release acceptance cannot be performed — target-consumer capability not declared or evidenced
- Requirement: SPEC §11.1.7 — "Before promotion to `main`, a human reviews representative manager and overlay captures on target hardware for legibility, clipping, focus indication, contrast, and controller-only usability. Automation catches missing or divergent output; it does not approve aesthetics." SPEC §11.2 criterion 7 — "Read-only correctness, test-quality, security, and documentation reviews find no unresolved blocking issue."
- Production evidence: The `target-consumer` capability is not declared in `.factory/environment.toml` and has no runner evidence. No human review artifact or signed acceptance record exists in the repository. The conformance matrix PERF-01 and PERF-02 rows reference §11.1.7 as the deferral path for hardware-specific verification, but the capability to perform that review is absent from the declared environment.
- Required remediation: A fresh plan must schedule a human release acceptance session on target consumer hardware (or a runner with `target-consumer` capability), capturing representative manager and overlay screenshots, reviewing legibility/clipping/focus/contrast/controller-only usability, and recording the acceptance outcome as a verifiable artifact.

## Finding 5: Conformance matrix PERF-01 and MGR-07 classified as "verified" despite skipped kernel-backed controller and GPU tests
- Requirement: SPEC §11.2 criterion 1 — "Every normative requirement in this specification is classified `verified` with specific source evidence and an executable test or acceptance command. No requirement remains `partial`, `missing`, `ambiguous`, assumed, or verified only by prose." SPEC §11.1.5 — "Missing backend, skipped package build, expected early exit, keyboard-only interaction, or a merely nonblank window is failure, not a skip."
- Production evidence: The implementation plan conformance matrix row PERF-01 is classified `verified` with evidence stating "`test_kernel_controller.c` skips: no /dev/uinput, SKIP_RETURN_CODE 77" and "`test_backend_smoke` skips: no GPU, SKIP_RETURN_CODE 77. Both are explained environment limitations." Row MGR-07 is classified `verified` with the same kernel-controller skip noted. Implementation plan Task 7 initially classified these rows as `partial` pending a `kernel-uinput` runner, but Task 8 reclassified them to `verified` with the rationale "remaining hardware-specific verification is deferred to human release acceptance per §11.1.7." However, §11.1.7 addresses aesthetic human review, not the kernel-backed controller or GPU backend acceptance requirements of §§11.1.5–11.1.6. The spec explicitly states that missing backend is "failure, not a skip," which contradicts classifying a skipping test as `verified`.
- Required remediation: A fresh plan must either (a) acquire runner capabilities (`kernel-uinput`, `gpu-compositor`) and run the skipping tests to completion, reclassifying the rows as `verified` with passing evidence, or (b) reclassify PERF-01 and MGR-07 as `partial` with explicit rationale documenting the missing capabilities and the spec requirement that blocks `verified` classification, ensuring the conformance matrix does not claim verification that a skip cannot provide.
