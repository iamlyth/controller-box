## Finding 1: Installed functional smoke test lacks physical or kernel-backed synthetic controller
- Requirement: SPEC §11.1.5 requires "hotplug a physical or kernel-backed synthetic controller, navigate Manager with real controller events." SPEC §5.7 states "Controller acceptance uses the production controller transport with a physical or kernel-backed synthetic gamepad while InputPlumber is running; keyboard-generated SDL events are supplemental accessibility evidence and must never be labeled controller acceptance."
- Production evidence: `tests/test_installed_binary.sh` (the installed binary subprocess test) uses `xdotool` keyboard and mouse events exclusively — no gamepad at all. `tests/test_installed_functional.c` (the in-process test) uses `SDL_JoystickAttachVirtual` / `SDL_JoystickSetVirtualButton` at line 122/172 — an SDL-userspace virtual joystick, not a kernel-backed evdev device. The test header at `tests/test_installed_functional.c:9` claims "Hotplug a kernel-backed SDL virtual game controller" but the implementation is SDL-only, not kernel-backed. `tests/test_manager_native.c` and `tests/test_manager_native_prof.c` also use `SDL_JoystickSetVirtualButton`, not uinput. The plan's Task 7 evidence explicitly acknowledges "kernel-backed virtual gamepad (uinput) not available in Nix-shell environment." The environment declares no runner with `physical-controller` or `kernel-gamepad` capability. The conformance matrix rows VS-01, MG-01–MG-14, OV-01–OV-11 are marked `verified` without noting that the controller transport is SDL-virtual or keyboard, not "physical or kernel-backed" as the spec requires.
- Required remediation: The next fresh plan must schedule a test that hotplugs a physical or kernel-backed synthetic controller (via uinput/evdev) and navigates the installed Manager binary with real gamepad events through the production event loop, or must declare a runner capability that provides this and produce exact-commit runner evidence.

## Finding 2: Installed functional smoke test lacks compositor-visible overlay activation
- Requirement: SPEC §11.1.5 requires "activate a mapped compositor-visible overlay, and verify persistence after process/backend restart." SPEC §4.10 requires deterministic visual verification of the overlay grid, Host Mode, conflict highlighting, and icons.
- Production evidence: `tests/test_installed_binary.sh` Phase 6 (line 246) launches `controller-box --overlay-service` and verifies the process stays alive and can query `InterceptMode` via `busctl`, but never triggers the overlay (no Select+A, no InterceptMode PASS→ALL transition through the binary) and never captures or verifies compositor-visible output. `tests/test_installed_smoke.sh` launches the overlay service but the captured frame mean is 0 (blank/hidden) — the overlay is never activated. `tests/test_installed_functional.c` Phases 7–10 (lines 495–595) claim "Overlay service initialization" and "Overlay activation via InterceptMode change" in comments, but the code only sets and reads `InterceptMode` via DBus wrapper functions — `cbx_overlay_service_init` and `cbx_overlay_service_step` are never called, no overlay context is created, and no framebuffer is verified. The overlay IS exercised through `cbx_overlay_service_step` in `tests/test_overlay_native.c` (in-process, native DBus) and `tests/test_overlay_visual.c` (in-process, synthetic data, framebuffer readback), but neither test executes the installed binary nor verifies compositor-visible output through the binary's own rendering path. No test combines installed binary execution + overlay activation + compositor-visible framebuffer verification.
- Required remediation: The next fresh plan must schedule a test that activates the overlay through the installed binary's production event path (InterceptMode PASS→ALL transition, overlay poll detection, surface show) and verifies compositor-visible framebuffer output (non-blank grid, player position indicators, controller text, virtual-device icons) through the binary's own SDL rendering pipeline.

## Finding 3: Boolean DBus property SET lacks native type fidelity
- Requirement: SPEC §10.1 states "production reads and writes each member using its declared DBus signature, including `u` for `InterceptMode`, `b` for booleans, and `as` for string arrays. Converting every property through a string getter is prohibited."
- Production evidence: `src/dbus/dbus_client.c:496-567` (`sd_set_property`) handles array properties (`as`) at lines 517-522 and uint properties (`u`, InterceptMode) at lines 528-535, but boolean properties (`ManageAllDevices: b`, `Enabled: b`) fall through to the string branch at lines 537-543, which opens a `v` variant with inner type `s` instead of `b`. The GET path (`sd_get_property` at lines 339-396) correctly handles `b` via `sd_bus_message_read(reply, "b", &boolean)`, but the SET path does not. The conformance matrix row DB-02 claims "Native type fidelity u/b/as/s — verified" citing "sd_get_property reads u/b/as/s natively" but does not address the SET path for booleans. If production code sets `ManageAllDevices` or `Enabled`, the value would be sent as a string variant (`v<s>`) instead of a boolean variant (`v<b>`), violating the native type fidelity requirement.
- Required remediation: The next fresh plan must schedule a fix to `sd_set_property` that writes boolean variants (`v<b>`) for boolean properties, and a test that verifies a boolean property SET round-trip through the native-signature DBus server.

## Finding 4: test_installed_functional.c overlay phases claim production coverage not delivered
- Requirement: SPEC §11.2.2 requires "All v1 workflows run through the same initialization, event dispatch, rendering, backend, persistence, and shutdown paths as the installed binaries. Test-only assembly or direct callback invocation may supplement but never replace production-path acceptance."
- Production evidence: `tests/test_installed_functional.c` header (lines 7–9) claims the test will "Activate a mapped compositor-visible overlay." Phase 7 comment (lines 498–501) claims "This exercises the full production init path: SDL renderer, DBus connect, enumerate, settings/assignments load, reconcile targets, surface build." Phase 8 comment (lines 521–526) claims "Overlay activation via InterceptMode change" and "The overlay's poll should detect this transition and activate." However, the actual code in Phases 7–10 (lines 503–595) only calls `ip_composite_set_intercept_mode` and `ip_composite_get_intercept_mode` — DBus property wrapper functions. No `cbx_overlay_service_ctx` is created, `cbx_overlay_service_init` is never called, `cbx_overlay_service_step` is never called, and no rendering or framebuffer verification occurs. The overlay lifecycle state machine, poll loop, surface activation, and input dispatch are not exercised. The `#include "app/overlay_service.h"` at line 63 is unused. This is a test-trust gap: the test's documentation claims production-path overlay coverage that the code does not deliver, and the conformance matrix VS-01 cites this test as evidence for the overlay activation requirement.
- Required remediation: The next fresh plan must either implement actual overlay service initialization, stepping, and rendering verification in this test (calling `cbx_overlay_service_init` and `cbx_overlay_service_step` through the production poll path), or correct the test comments and conformance matrix to accurately reflect that only DBus property round-trips are tested, not overlay lifecycle activation.

## Finding 7: DBus InterfacesAdded/Removed signals lack sender verification
- Requirement: SPEC §10.1 states "Hotplug: subscribe to ObjectManager InterfacesAdded / InterfacesRemoved — source, composite, and target devices all register/unregister through the object server." SPEC §2.4 requires the GUI to process DBus traffic and reconcile after service/device changes. The production code verifies sender for NameOwnerChanged (match rule filters `sender='org.freedesktop.DBus'`, `arg0='org.shadowblip.InputPlumber'`) and for PropertiesChanged (delegates to `ip_properties.c:sender_ok()`), but not for hotplug signals.
- Production evidence: `src/dbus/dbus_client.c:55-130` (`sd_interfaces_added_callback`) and `:134-175` (`sd_interfaces_removed_callback`) filter on interface and member but do not verify that the signal sender matches InputPlumber's unique bus name. The `sender` field is passed through to the callback payload but no downstream code checks it against the known InputPlumber unique name (which is tracked in `ip_connection.c`). A malicious DBus service on the system bus could send spoofed `InterfacesAdded`/`InterfacesRemoved` signals that would be processed as if they came from InputPlumber, causing spurious device enumeration or removal. This is a defense-in-depth gap — the system bus is generally trusted, and polkit restricts who can claim the InputPlumber name, but the inconsistency with PropertiesChanged sender verification is a security weakness.
- Required remediation: The next fresh plan must schedule addition of sender verification for InterfacesAdded/Removed callbacks, comparing the signal sender against InputPlumber's tracked unique bus name, consistent with the existing PropertiesChanged sender verification.
