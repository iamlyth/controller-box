## Finding 2: Controller acceptance uses process-local SDL virtual gamepads, not the physical or kernel-backed synthetic gamepad required by SPEC
- Requirement: SPEC §5.7: "Controller acceptance uses the production controller transport with a physical or kernel-backed synthetic gamepad while InputPlumber is running; keyboard-generated SDL events are supplemental accessibility evidence and must never be labeled controller acceptance." SPEC §11.1.5: "hotplug a physical or kernel-backed synthetic controller." SPEC §11.2.3: "Every enabled control in the §5.7 inventory has passing controller and pointer activation evidence."
- Production evidence: `tests/test_installed_functional.c:251` uses `SDL_JoystickAttachVirtual(SDL_JOYSTICK_TYPE_GAMECONTROLLER, ...)` — a process-local virtual device that never touches the kernel evdev layer. `tests/test_manager_native.c:167` uses the same process-local API. `tests/test_kernel_controller.c` would provide kernel-backed evidence via `/dev/uinput` but skips with exit 77 (line 350) because `/dev/uinput` is unavailable. The `kernel-uinput` and `physical-controller` capabilities are not declared in `.factory/environment.toml`. The installed functional evidence file (`.factory-state/installed-functional-evidence.env`) records `result=PASS` but the test's own header comment (line 9) claims "kernel-backed SDL virtual game controller" while the implementation is process-local. MGR-36 and DOD-03 remain `partial` in the conformance matrix.
- Required remediation: Run `test_kernel_controller.c` to completion (exit 0, not 77) on a runner with `/dev/uinput` access, and either augment `test_installed_functional.c` to use the kernel-backed controller path or add a separate test that exercises the installed binary with kernel-backed evdev input through the full manager and overlay workflow. Record exact-commit runner evidence for `kernel-uinput` or `physical-controller`.

## Finding 6: Manager init does not load persisted settings before computing expected controller count
- Requirement: SPEC §7.3: settings are persisted and loaded at startup. SPEC §11.2.2: "All v1 workflows run through the same initialization, event dispatch, rendering, backend, persistence, and shutdown paths as the installed binaries." SPEC §5.2: "The configured startup count/type list is authoritative desired topology."
- Production evidence: `src/manager/manager.c:233-234` calls `cbx_settings_defaults(&mgr->settings)` but never calls `cbx_settings_load` during manager initialization. The overlay service does load settings (`src/app/overlay_service.c:1140`). Consequently, `cbx_controllers_tab_set_expected_count` at `manager.c:314` receives the default count (4) rather than the user's persisted count, potentially causing false orphan-column errors if the user configured a different count. The settings tab loads settings on refresh, but the manager's initial topology reconciliation uses defaults.
- Required remediation: Call `cbx_settings_load` (or equivalent) during `cbx_manager_init_with_dbus` after defaults are set and before the controllers tab is initialized, so the manager starts with the user's persisted virtual controller count and types. Add a regression test that saves a non-default count, reinitializes the manager, and verifies the expected count matches the saved value.

## Finding 7: Production DBus interface header resides in the test directory
- Requirement: SPEC §11.2.2: "Test doubles must preserve external type/signature semantics." SPEC §11.2.5: "no ... test-only production bypasses." The core DBus backend interface (`ip_dbus_backend` vtable, `ip_bus_handle`, all signal payload structs) is defined in `tests/dbus_mock.h`, which 28+ production source files include.
- Production evidence: `CMakeLists.txt:153` adds `"${CMAKE_CURRENT_SOURCE_DIR}/tests"` to the public include path. Every `src/dbus/*.c` and key headers like `src/manager/manager.h:32` and `src/app/overlay_service.h:16` include `dbus_mock.h` from the tests directory. The header name implies test-only status, but it defines the production interface. If the tests directory were excluded from a production build, compilation would fail. This is an architectural hygiene issue, not a functional bug — the vtable pattern is sound and `dbus_client.c` provides real sd-bus implementations.
- Required remediation: Move the DBus interface definitions (vtable struct, handle type, signal payload structs, `ip_dbus_sd_backend()` declaration) from `tests/dbus_mock.h` to a production header in `src/dbus/` (e.g., `dbus_interface.h`). Update all production includes. The mock-specific code can remain in the test directory.
